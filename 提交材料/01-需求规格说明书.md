## 一、引言

### 1.1 编写目的

本文档把已确认的需求基线（`00-需求确认清单.md`）展开为**可开发、可测试、可验收**的规格说明，
供开发、测试、评审三方共用：

- 开发方据此判断"做到什么程度算完成"
- 测试方据此编写测试用例（D5 的用例全部以本文的"验收标准"为依据）
- 评审方据此核对交付物是否覆盖需求

**本文档不重复讨论"为什么这么定"**——那些决策理由记录在需求确认清单中，本文只描述"要做成什么样"。

### 1.2 项目背景与范围

高校选课系统面向**单个学期、一轮选课窗口**的教学场景，覆盖学生选退课、教师查看选课情况、
管理员维护课程与窗口的完整闭环。

**本期范围**（需求基线 §2.1）：6 项核心功能 + 2 项流程增强 + 3 项支撑能力，共 11 项。

**明确不做**（需求基线 §2.2）：志愿抽签与分轮选课、学生自主注册、跨校区通勤冲突、
学分统计与培养方案、先修课校验、选课日志审计、课表导出、课程评价、Docker 部署。

### 1.3 术语与缩略语

| 术语 | 说明 |
| --- | --- |
| 课程（course） | 本系统中指**某学期的一门开课班次**，含授课教师、容量与排课 |
| 节次（period） | 一天内的时间片，1~12 节，与钟点时间的映射见 `src/config.js` |
| 周次（week） | 学期内的第 N 周，默认 1~16 周 |
| 单双周 | 课程只在单周或双周上课；单周课与双周课即使同一时段也不冲突 |
| 候补队列 | 课程满员后的排队机制，按进入候补的时间先进先出 |
| 补位 | 有学生退课时，候补队首自动获得名额 |
| 选课窗口 | 允许选课的时间区间，由管理员配置 |

## 二、总体描述

### 2.1 产品前景

系统替代"Excel 登记 + 人工核验时间冲突"的传统做法，解决三个具体痛点：

| 痛点 | 本系统的解决方式 |
| --- | --- |
| 多人同时选课容易超额 | 事务内实时校验余量，并发下不超卖（E2） |
| 时间冲突靠人工比对易错 | 程序化判定"星期 + 节次 + 周次"三条件 |
| 满员后无法排队 | 候补队列 + 退课自动补位 |

### 2.2 用户角色与特征

| 角色 | 数量（演示数据） | 特征与关注点 |
| --- | --- | --- |
| 学生 | 40 | 关心能否选上、是否冲突、候补排到第几；操作频繁、集中在选课高峰期 |
| 教师 | 12 | 关心自己所授课程的学生名单与人数；操作频率低 |
| 管理员 | 1 | 维护课程与选课窗口、发布公告、查看统计；操作频率低但影响全局 |

**权限边界**（需求基线 A 组）：

| 能力 | 学生 | 教师 | 管理员 |
| --- | --- | --- | --- |
| 登录 / 退出 | ✅ | ✅ | ✅ |
| 课程查询与详情 | ✅ | ✅ | ✅ |
| 查看公告 | ✅ | ✅ | ✅ |
| 选课 / 退课 / 候补操作 | ✅ | ❌ | ❌ |
| 查看自己所授课程的名单 | — | ✅ | ❌ |
| 查看授课时间冲突 | — | ✅ | ❌ |
| 管理课程 / 窗口 / 公告 | ❌ | ❌ | ✅ |

### 2.3 运行环境

| 项 | 要求 |
| --- | --- |
| 操作系统 | Windows / macOS / Linux（本机开发环境为 Windows） |
| 运行时 | Node.js ≥ 20 |
| 数据库 | SQLite（单文件，无需安装服务）→ **2026-10-22 演进为 PostgreSQL**（见文末变更说明） |
| 浏览器 | Chrome / Edge / Firefox 等现代浏览器 |
| 网络 | 本地运行无需联网；首次安装依赖需联网 |

### 2.4 设计与实现约束

| 约束 | 来源 | 影响 |
| --- | --- | --- |
| 必须避开需要原生编译的依赖（`node-gyp`） | F1（本机缺 Visual Studio 编译工具链） | 数据库驱动选 `node-sqlite3-wasm`，口令用内置 `crypto.scrypt` |
| 采用 Node.js + Express + SQLite + 原生 HTML/CSS/JS | F1 | 不引入前端构建工具与框架 |
| 不提供 Dockerfile | F2 | 交付以"解压即用"的启动器形式提供 |
| 需提供在线演示链接 | F3 | 见 7.2 遗留项 |
| 文档需可导出 Word / PDF | F4 | 文档以 Markdown 存档，另提供转换方式 |

### 2.5 假设与依赖

| 假设 | 若不成立的影响 |
| --- | --- |
| 一个学期只有一轮选课窗口 | 需要引入多轮次模型（已列为演进预案） |
| 一门课只有一个班次、一个主讲教师 | 需要拆分 `course_offering` 表 |
| 学生与教师账号由管理员预置，不开放注册 | 需增加注册与审核流程 |
| 运行在单进程环境 | 多进程部署时并发保障需重新评估（L1） |

## 四、功能需求

> 每项包含：描述、参与者、优先级、前置条件、主流程、异常流程、后置条件、验收标准。
> 验收标准写成**可测的断言**，D5 测试报告的用例直接来源于此。

### FR-01 课程查询（对应 §2.1-1）

| 项 | 内容 |
| --- | --- |
| 描述 | 按条件检索本学期的开课列表，并查看单门课程的详情 |
| 参与者 | 学生、教师、管理员 |
| 优先级 | 高 |
| 前置条件 | 已登录；系统已配置当前学期 |

**主流程**

1. 用户进入"课程查询"页；
2. 系统展示当前学期全部课程（默认按课程代码升序），每门课显示：代码、名称、教师、学分、上课时间、容量/已选、状态；
3. 用户可选填检索条件（课程名或代码、开课院系、授课教师、上课星期）并提交；
4. 系统按条件过滤后重新展示结果，并显示命中数量；
5. 用户点击某门课程，系统展示详情：上课时间（含单双周与周次区间）、地点、简介、容量/已选/余量/候补人数。

**异常流程**

| 编号 | 情况 | 系统响应 |
| --- | --- | --- |
| E1 | 无匹配结果 | 显示"没有符合条件的课程，换个条件试试。" |
| E2 | 课程 id 不存在 | 返回 404 页面 |
| E3 | 系统未配置学期 | 列表显示"尚未配置学期"，课程数为 0，不报错 |
| E4 | 课程未排课 | 上课时间列显示"未排课" |

**后置条件** 无数据变更。

**验收标准**

- AC-01-1：课程列表返回 33 门（演示数据），检索"数据结构"命中 1 门，检索代码 `CS10` 命中 9 门；
- AC-01-2：按院系筛"数学学院"命中 8 门；按星期筛"周一"命中 6 门；
- AC-01-3：满员课程在详情页显示"名额已满"；停开课程显示"停开"；
- AC-01-4：学生登录时，列表额外标注自己的选课状态（已选 / 候补中）。

### FR-02 选课（对应 §2.1-2）

| 项 | 内容 |
| --- | --- |
| 描述 | 学生选定课程并提交，系统实时校验后占用名额 |
| 参与者 | 学生 |
| 优先级 | 高 |
| 前置条件 | 已登录且角色为学生；课程存在且属于当前学期 |

**主流程**

1. 学生在列表或详情页点击"选课"；
2. 系统在**单个数据库事务**内依次校验：选课窗口是否开放 → 课程是否停开 → 是否已选中或已在候补 → 是否与已选课程时间冲突 → 余量是否足够（校验顺序见 R6）；
3. 校验全部通过且有余量：写入 `enrolled` 状态，占用一个名额；
4. 系统跳回来源页并提示"选课成功：课程名"。

**异常流程**

| 编号 | 情况 | 提示 |
| --- | --- | --- |
| E1 | 选课窗口未开放/已截止 | "选课已于…截止，当前不可选课" |
| E2 | 课程已停开 | "该课程已停开，不可选课" |
| E3 | 已经选中该课 | "你已经选中了「课程名」" |
| E4 | 已在该课候补队列中 | "你已经在「课程名」的候补队列中" |
| E5 | 与已选课程时间冲突 | "与已选课程时间冲突：课程A（代码）、课程B（代码）" |

**后置条件** 成功时新增或更新一条 `enrollment` 记录。

**验收标准**

- AC-02-1：余额充足时选课成功，`enrolled` 计数 +1；
- AC-02-2：重复提交同一门课被拒绝，且不产生第二条记录（`UNIQUE(student_id, course_id)` 保证）；
- AC-02-3：与已选课程时间重叠时被拒绝，提示中列出冲突课程名；
- AC-02-4：**10 名学生并发抢容量为 3 的课程，最终选中人数恰为 3，不超卖**（E2/E3）。

### FR-03 退课（对应 §2.1-3）

| 项 | 内容 |
| --- | --- |
| 描述 | 学生退选已选课程，释放名额；若候补队列非空则自动补位 |
| 参与者 | 学生 |
| 优先级 | 高 |
| 前置条件 | 已登录且为该校课程的 `enrolled` 记录持有者 |

**主流程**

1. 学生在"我的选课"或课程详情页点击"退课"（需二次确认）；
2. 系统校验该生确实处于 `enrolled` 状态；
3. 置为 `dropped`，清空 `waitlist_joined_at`；
4. 触发候补补位（见 FR-07）；
5. 跳回来源页并提示退课结果；若发生补位，提示中说明补位到谁。

**异常流程**

| 编号 | 情况 | 提示 |
| --- | --- | --- |
| E1 | 未选中该课程 | "你尚未选中「课程名」" |
| E2 | 课程已不存在 | "课程不存在" |

**关键规则**

- **退课不受选课窗口限制**（B3）：窗口截止后学生仍可退课；
- 退课后可重新选同一门课，但须**重新排入候补队尾**（R9）。

**验收标准**

- AC-03-1：退课后该课程从"我的选课"中消失，已选人数 −1；
- AC-03-2：把选课截止时间改为过去后，退课仍然成功；
- AC-03-3：退课后若有人候补，队首学生自动变为 `enrolled`，且该动作同样不受窗口影响（R3）。

### FR-04 人数限制（对应 §2.1-4）

| 项 | 内容 |
| --- | --- |
| 描述 | 以课程容量为上限控制选课人数，满员后不再接受直接选课 |
| 参与者 | 学生（受约束）、管理员（设容量） |
| 优先级 | 高 |
| 前置条件 | 课程已设置容量 |

**规则**

1. 容量按课程单独设置，取值 0~500 的整数；
2. 已选人数 = 该课程 `status='enrolled'` 的记录数；
3. 余量 = 容量 − 已选人数，且不小于 0；
4. 已选人数 ≥ 容量时，选课转为候补（FR-07），不再占用名额；
5. 容量判定必须基于**事务内实时计数**，不得使用页面上显示的旧数字。

**验收标准**

- AC-04-1：容量 2 的课程已满时，详情页显示"名额已满"；
- AC-04-2：并发提交后已选人数恰好等于容量，不出现 `capacity + 1`；
- AC-04-3：管理员把容量改小到低于当前已选人数时，系统不强制退课，只是不再接受新选课。

### FR-05 时间冲突检查（对应 §2.1-5）

| 项 | 内容 |
| --- | --- |
| 描述 | 判断待选课程是否与已选课程在时间上冲突 |
| 参与者 | 学生（间接受益）、系统内部 |
| 优先级 | 高 |
| 前置条件 | 课程已排课；学生有已选课程 |

**判定式（R4）**

> 两门课冲突 ⟺ **星期相同** 且 **节次区间真正重叠** 且 **周次集合有交集**

| 条件 | 判定方式 | 依据 |
| --- | --- | --- |
| 星期 | `day_of_week` 相等 | C1 |
| 节次 | `a.start ≤ b.end 且 b.start ≤ a.end`（闭区间） | C3：**相邻时段不算冲突** |
| 周次 | 展开"每周/单周/双周 + 起止周"后求交集 | C2 / R5 |

**验收标准**

- AC-05-1：第 1-2 节与第 3-4 节**不冲突**；第 1-2 节与第 2-3 节冲突；
- AC-05-2：单周课与双周课同一天同一时段**不冲突**；单周与每周冲突；
- AC-05-3：周次区间不相交（1-8 vs 9-16）不冲突；首尾相接（1-8 vs 8-16）冲突；
- AC-05-4：判定逻辑有独立单元测试覆盖，共 **26 项**。

### FR-06 选课结果查询（对应 §2.1-6）

| 项 | 内容 |
| --- | --- |
| 描述 | 学生查看本人的已选课程与候补情况；管理员查看各课程选课统计 |
| 参与者 | 学生、管理员 |
| 优先级 | 中 |
| 前置条件 | 已登录 |

**学生视角**

1. 展示已选课程列表：代码、名称、教师、学分、上课时间；
2. 展示合计已选门数与合计学分；
3. 展示候补队列：课程、**我的位次**、候补总人数；
4. 可在此页直接退课或退出候补。

**管理员视角**

1. 按已选人数降序展示各课程；
2. 每行显示：已选 / 容量 / 候补 / 满员率（进度条 + 百分比）。

**验收标准**

- AC-06-1：学生 `2024010101` 登录后显示已选 4 门、13.0 学分、候补 0 门；

### FR-00 用户登录与角色鉴权（基础能力，对应 A4）

虽不在 §2.1 的 11 项功能内，但为全部功能的前置能力，一并说明。

| 项 | 内容 |
| --- | --- |
| 描述 | 学号/工号 + 密码登录，按角色进入对应首页并限制可访问路径 |
| 参与者 | 全部 |
| 优先级 | 高 |

**规则**

1. 账号为学生学号或教师/管理员工号，全局唯一；
2. 口令以 `scrypt` 加盐派生存储，数据库中不存明文；
3. 登录失败返回 401 并提示，不透露"账号是否存在"；
4. 未登录访问受保护页面：GET 跳登录页（带 `next` 参数），非 GET 的表单请求同样跳登录页；仅声明 `Accept: application/json` 的请求返回 401 JSON；
5. 角色不符返回 403。

**验收标准**

- AC-00-1：三个演示账号均可登录并进入对应首页；
- AC-00-2：错误密码返回 401；
- AC-00-3：学生访问 `/admin/**`、`/teacher/**` 返回 403；教师访问 `/admin/**` 返回 403；
- AC-00-4：未登录访问 `/courses` 返回 302 并携带 `next=/courses`。

| 数据库 | SQLite 单文件 | **PostgreSQL 18**（Neon），SQLite 保留为离线/回退 | 需要"本地与线上共用同一个库"；SQLite 单文件无法跨机器共享 |
| 技术约束 F1 | "技术栈固定为 Node + Express + SQLite + 原生前端" | Node + Express + 数据库（SQLite/PostgreSQL 双驱动）+ 原生前端 | F1 的**实质约束是不引入原生编译**（本机缺 VS 工具链），该约束仍满足：`pg` 也是纯 JS |
| NFR-P4 容量 | "4.2 MB，SQLite 无压力" | 单机规模不变；云端走免费额度（1 GB），实测占用远低于上限 | 数据量未变，只是承载方式变了 |

**未受影响的部分**：功能需求 FR-00~FR-11、业务规则 R1~R9、验收标准 AC-xx-n 全部不变，
118 项测试断言也未修改——迁移只换了存储实现，没有改业务语义。
