# 01 · 架构与代码地图

> 回答：代码分几层？每个文件负责什么？一次请求是怎么走完的？

---

## 一、整体架构

采用**分层架构**，请求自上而下穿透，每层只做一件事：

```
浏览器
  │  HTTP 请求（表单提交 / 页面跳转）
  ▼
┌──────────────────────────────────────────────┐
│ 路由层  src/routes/*.js                       │  解析参数、鉴权、调服务、选模板
├──────────────────────────────────────────────┤
│ 服务层  src/services/*.js                     │  业务规则（冲突判定、余量校验、候补补位）
├──────────────────────────────────────────────┤
│ 数据访问层  src/db/index.js                   │  连接管理、参数规整、事务封装
├──────────────────────────────────────────────┤
│ 存储层  SQLite（data/course-selection.sqlite）│  表、约束、索引
└──────────────────────────────────────────────┘
  │
  ▼
EJS 模板渲染 HTML → 浏览器
```

### 分层职责边界（重要）

| 层 | 可以做什么 | **不可以**做什么 |
| --- | --- | --- |
| 路由层 `routes/` | 读 `req`、鉴权、调服务、`res.render` | ❌ 不写 SQL，❌ 不写业务规则判断 |
| 服务层 `services/` | 组合多次数据库操作、执行业务规则、开启事务 | ❌ 不碰 `req` / `res`，❌ 不渲染模板 |
| 数据访问层 `db/` | 执行 SQL、参数规整、事务 | ❌ 不含业务语义（不认识"选课"这个词） |
| 视图层 `views/` | 展示数据、提交表单 | ❌ 不查数据库 |

> **为什么强调这个**：业务规则（比如"满员转候补"）如果写进路由层，将来做并发压测脚本、写单元测试就没法复用。放服务层才能被 HTTP 和脚本同时调用。

## 三、一次请求的完整生命周期

以「学生提交选课」为例：

```
1. 浏览器 POST /enrollments （表单含 courseId）
        │
2. app.js 中间件链
        ├── express.urlencoded   解析表单
        ├── express.static       静态资源（本条请求不命中，继续）
        ├── express-session      从 Cookie 取会话
        └── attachUser           把用户信息放进 req.user 和 res.locals
        │
3. routes/enrollments.js
        ├── requireLogin         未登录 → 302 跳登录页
        ├── requireRole('student') 角色不符 → 403 错误页
        ├── 读取 req.body.courseId
        └── 调用 enrollmentService.enroll(studentId, courseId)
                │
4. services/enrollmentService.js
        └── db.transaction(...)  ← BEGIN IMMEDIATE，全程持锁
                ├── 校验选课窗口是否开放        （B2）
                ├── 校验是否已选过该课           （重复选课）
                ├── 校验时间是否冲突             （C1~C3，调 conflictService）
                ├── 查询余量                    （F4）
                ├── 有余额 → 写入 enrolled      （F2）
                └── 无余额 → 写入 waiting       （B4 候补）
        │
5. db/index.js
        └── 执行 SQL，返回结果
        │
6. 回到路由层
        ├── 成功 → 重定向并闪现提示
        └── 失败 → 带错误信息回到课程列表
```

**关键点**：第 4 步的整段校验 + 写入必须在**同一个事务**里，否则并发下会出现"余量明明还有 1 个，两个人都选上了"的超卖问题（对应需求 E2）。

## 四、关键设计决策记录

| 决策 | 理由 |
| --- | --- |
| 用 SQLite 而非 MySQL | 单文件、免安装免配置，作业演示场景够用，也避免交作业时对方要装数据库服务 |
| 用 `node-sqlite3-wasm` 而非 `better-sqlite3` | 本机 Windows 缺 Visual Studio 编译工具链，原生模块编译必然失败 |
| 前端用服务端渲染 EJS，不用 Vue/React | 无需构建工具，打开即跑，演示环节最稳，排查成本最低 |
| 口令用 Node 内置 `crypto.scrypt`，不用 bcrypt | bcrypt 需原生编译；scrypt 是标准库，安全强度足够且零依赖 |
| 业务规则集中在 `services/` | 便于被 HTTP 路由和并发压测脚本共用，也便于写测试 |
| `course` 表同时代表"课程"和"开课班次" | 简化模型：本系统一个学期内一门课只有一个班次。若将来要支持同课多班，需拆出 `course_offering` 表——见 `02-数据库设计说明` 的扩展点 |
| 数据库结构只在 `schema.sql` 维护 | 单一事实来源，避免建表语句散落在代码里 |

## 五、扩展点速查

| 想扩展的能力 | 需要动的地方 |
| --- | --- |
| 增加角色（如助教） | `config.js` 的 `roles`、`schema.sql` 里 `user.role` 的 CHECK 约束、各路由的 `requireRole(...)`、`views/partials/header.ejs` 的导航分支 |
| 一门课多个班次 | 拆出 `course_offering` 表，`class_time` / `enrollment` 改指向它 |
| 增加选课轮次 | `semester` 增加轮次字段或新建 `selection_round` 表，窗口校验改读它 |
| 记录操作日志 | 新增 `operation_log` 表 + 在服务层写日志（当前需求 D3 明确不做） |
| 换数据库 | 只需重写 `src/db/index.js`，上层服务与路由不用改——这正是分层的价值 |
