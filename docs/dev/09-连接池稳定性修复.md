# 连接池稳定性修复（2026-10-22）

## 现象

迁移到 Neon 后，线上偶发**页面 500 或连接中断**（smoke 中表现为 `HTTP 000`）。
Render 日志：

```
Error: Connection terminated unexpectedly
    at pg-pool/index.js:45
    at async Object.all (src/db/pg.js)
```

本地跑脚本时同样出现，说明与部署环境无关。

## 原因

托管 PG（Neon 的 PgBouncer）会在服务端回收长时间空闲的连接。
而本项目的连接池 `idleTimeoutMillis` 设为 30 秒，池子仍认为那条连接可用；
下一条查询取到它时，服务端已经断开 → 报 `Connection terminated unexpectedly`。

> 这类问题在 SQLite 模式下不存在（进程内文件句柄，无网络）。

## 修法（`src/db/pg.js`）

| 改动 | 说明 |
| --- | --- |
| `idleTimeoutMillis: 30000 → 10000` | 早于服务端回收，主动丢弃空闲连接 |
| `keepAlive: true` + `keepAliveInitialDelayMillis: 5000` | 让 TCP 层尽早发现死连接 |
| 读操作 `queryWithRetry`（重试 1 次，间隔 150ms） | `get` / `all` 遇到连接类错误时重试 |

**为什么只给读操作加重试**：写操作若在提交后才断开，重试可能造成重复写入。
本项目写路径都走事务且带业务校验，宁可让用户重试一次，也不能重复记账。

## 验证

| 场景 | 结果 |
| --- | --- |
| 本地连续 30 次查询 | **0 失败**（修复前会出现断连） |
| SQLite 模式全量回归 | 118/118（说明改动不影响离线模式） |
| 线上冒烟 | 见下方提交后的实测 |

## 经验

**托管数据库的"空闲连接回收"是必踩的坑**：连接池的 idle 超时必须小于服务端的回收阈值，
否则池里会积累"看起来活着、实际已断"的连接。表现为偶发、不可复现的 500。
