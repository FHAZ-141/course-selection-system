**执行中新发现的问题（原方案未预料）**

> **`user` 是 PostgreSQL 的保留字**，`CREATE TABLE user` 与 `SELECT * FROM user` 都会语法错误。
> 本项目有 30+ 处 SQL 涉及该表。

处理方式（已实现）：

| 位置 | 做法 |
| --- | --- |
| 建表 | `schema.pg.sql` 中写 `"user"`（带引号，确保小写表名） |
| 查询 | `pg.js` 的 `quoteReservedIdentifiers()` 在 **表位置**（`FROM` / `JOIN` / `INTO` / `UPDATE` 之后）自动补引号 |
| 为什么不逐条改 SQL | 30+ 处容易漏；且会污染业务代码 |
| 为什么不重命名表 | 要同步改 SQLite schema、20+ 处 SQL、D4 与 U7 文档，改动面远大于收益 |
| 风险控制 | 只在单词边界 + 前置关键字匹配，不误伤 `username`、不误伤字符串字面量；已用 7 条单测覆盖 |

**另一处修正**：方案原写 `credits NUMERIC(3,1)`，实际改用 `DOUBLE PRECISION`。
原因：`node-postgres` 把 `NUMERIC` 解析成**字符串**，而现有代码把学分当数字用（求和 `totalCredits`、格式化），会出错。

#### 3.4 环境差异记录（已处理）

**发现**：本地 Node v22.22.2，Render 实际使用 **v26.12.0**——`engines: ">=20"` 是开放区间，
Render 选了最新版，跨 4 个大版本。

**决策**：把线上钉到本地已充分验证的 22.x，**而不是**把本地升到 26。

| 理由 | 说明 |
| --- | --- |
| 验证充分度不对称 | 22 上跑过完整 118 项（含并发 15 项）；26 上只跑过 77 项冒烟 |
| 方向原则 | 不应用「只验证过 77 项的环境」替换「验证过 118 项的环境」 |
| LTS 支持 | Node 22 为 LTS，支持到 2027-04 |
| 无原生模块 | 本项目依赖全为纯 JS，版本切换不涉及重新编译 |

**改动**：`package.json` 的 `engines` 由 `">=20"` 改为 `"22.x"`（提交 `9439559`）。

**结果**：

| 检查 | 结果 |
| --- | --- |
| Render 构建 | 成功，部署 `9439559` 状态 **Live** |
| 线上冒烟 | **77 / 77 全部通过** |
| `/health` | 200，1.85s |

**未能直接验证的一点（如实记录）**：
想从构建日志里读 `Using Node.js version 22.x` 那一行做直接证据，但 Render 的日志面板是**虚拟滚动**，
向上抓取多次不稳定（工具超时），没能截到。

现有证据链（间接但成立）：

1. 上一次部署的日志明确显示 Render 会读 `package.json` 的 engines：
   `Requesting Node.js version >=20` → `Using Node.js version 26.12.0 via …/package.json`
2. 本次 engines 改为 `22.x` 后，**构建成功**——若无法满足该区间，构建会报错中止
3. 新部署功能复测 77/77 通过

> 改进建议（未执行）：给 `/health` 增加 `node: process.version` 与 `commit: process.env.RENDER_GIT_COMMIT`，
> 之后所有版本/提交核对都能用一条 HTTP 请求完成，不必再翻日志。P2 之前做收益最大。

## 四、中断恢复手册

> 任何时刻中断，先判断"代码处于什么状态"，再决定继续还是回退。

### 4.1 第一步：查看当前状态

```bash
cd course-selection-system
git branch --show-current     # 在哪个分支
git status --short            # 有哪些改动没提交
git log --oneline -3          # 最后几步做了什么
```

### 4.2 场景 A：改到一半中断，改动未提交

```bash
# 想继续：先跑测试看是否还正常
npm run test:conflict && npm run stress

# 想放弃这批改动：全部丢弃，回到最后一次提交
git checkout -- .
git clean -fd src/db/          # ⚠️ 只清理 src/db 下的新增文件，避免误删 data/
```

### 4.3 场景 B：已提交但测试挂了

```bash
# 看是哪个套件挂
npm run test:conflict
npm run stress

# 单独回退这一步
git revert <出问题的sha>
```

### 4.4 场景 C：担心本地数据库被改坏

```bash
# 检查文件是否还在、大小是否正常
ls -l data/course-selection.sqlite      # 正常应为 110,592 字节

# 如果丢了或坏了：重建演示数据（会覆盖，但演示数据本来就是可重建的）
npm run init-db

# 彻底重建
npm run reset-db
```

> 本次改造**不会**主动碰这个文件；测试全部用 `DB_FILE` 指向临时目录。

### 4.5 场景 D：分支乱了想重来

```bash
git checkout main
git branch -D feat/pg-migration
git checkout -b feat/pg-migration      # 从干净的 main 重新开始
```

### 4.6 场景 E：线上出问题（P4 阶段才可能发生）

```bash
# Render 控制台 → 服务 → Environment → 删除 DATABASE_URL
# 或本地：
# 取消环境变量后重新部署，自动回退到 SQLite
```
