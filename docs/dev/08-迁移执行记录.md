**执行中新发现的问题（原方案未预料）**

> **`user` 是 PostgreSQL 的保留字**，`CREATE TABLE user` 与 `SELECT * FROM user` 都会语法错误。
> 本项目有 30+ 处 SQL 涉及该表。

处理方式（已实现）：

| 位置 | 做法 |
| --- | --- |
| 建表 | `schema.pg.sql` 中写 `"user"`（带引号，确保小写表名） |
| 查询 | `pg.js` 的 `quoteReservedIdentifiers()` 在 **表位置**（`FROM` / `JOIN` / `INTO` / `UPDATE` 之后）自动补引号 |
| 为什么不逐条改 SQL | 30+ 处容易漏；且会污染业务代码 |
| 为什么不重命名表 | 要同步改 SQLite schema、20+ 处 SQL、D4 与 U7 文档，改动面远大于收益 |
| 风险控制 | 只在单词边界 + 前置关键字匹配，不误伤 `username`、不误伤字符串字面量；已用 7 条单测覆盖 |

**另一处修正**：方案原写 `credits NUMERIC(3,1)`，实际改用 `DOUBLE PRECISION`。
原因：`node-postgres` 把 `NUMERIC` 解析成**字符串**，而现有代码把学分当数字用（求和 `totalCredits`、格式化），会出错。

### P1 开工计划（执行前预写）

**目标**：把服务层与路由层全部改为异步，为 PG 驱动铺路。**业务规则一条不改**。

**为什么必须一次做完**：改到一半时测试必然红（服务返回 Promise，路由没 await），
不存在"绿的中途点"。所以 P1 是一个原子改动，做完跑完整 118 项。

| # | 文件 | 操作 | 注意 |
| --- | --- | --- | --- |
| 1 | `src/db/sqlite.js` | `transaction(fn)` 改为 `async`，内部 `await fn()` | **关键**：同步 COMMIT 会在 async 回调完成前执行，导致事务失效 |
| 2 | `src/services/*.js`（8 个） | 函数加 `async`；`db.xxx` 与跨服务调用加 `await` | 跨服务链：enrollment → conflict → classTime |
| 3 | `src/routes/*.js`（7 个） | handler 改 `async (req,res)`；服务调用加 `await` | 漏 await 的症状：渲染出 Promise |
| 4 | `src/db/seed.js` | 整体异步化 | 被 `start:prod` 调用，必须 `await` |
| 5 | `test/stress-test.js` | 异步化 | 断言逻辑不变 |
| 6 | `src/server.js` | 启动时 `await db.initSchema()` | PG 驱动下 initSchema 是异步的 |

**验收**：118 项在 SQLite 模式全绿（与基线逐项一致）。
**回滚**：`git revert <P1 sha>`，或回到分支上一提交。

| --- | --- | --- | --- |
| `test:conflict` | 26/26 | **26/26** | ✅ |

**转换规模**：8 个服务 + 8 个路由 + `seed.js` + `stress-test.js` + `server.js` + `sqlite.js`，
共 **45 处函数异步化、约 190 行加 `await`**。

**过程中撞到并修复的 5 类问题**（都是"机械加 await"会漏的坑）：

| # | 问题 | 现象 | 修法 |
| --- | --- | --- | --- |
| 1 | **同文件裸函数调用**未 await | `const course = getCourseRow(id)` → 拿到 Promise，`course.id` 为 undefined | 先算出"哪些函数变异步"，再对兄弟函数调用补 await |
| 2 | **属性链优先级** | `await db.get(...).c` 等价于 `await (db.get(...).c)` → 得到 undefined | 一律改成 `(await db.get(...)).c`；共 12 处（seed 7 / admin 4 / teacher 1） |
| 3 | **同步遍历里不能用 await** | `.map()/.find()/.findIndex()` 的回调加 await 会语法错误 | 改成 `for...of` 循环（enrollmentService 的候补位次、stress 的两个查找） |
| 4 | **handler 写法不全** | `(req, res, next) =>` 未被替换成 async | 补上该模式；routes 里的辅助函数（buildStats / parseClassTimes / parseCourse / renderCourseForm）也要 async |
| 5 | **事务提交早于回调完成** | `transaction(fn)` 若不 `await fn()`，`COMMIT` 会在异步回调跑完前执行，事务失效 | sqlite 驱动改成 `async transaction` 并 `await fn()`（**最关键的一处**） |

> 第 5 条是最隐蔽的：语法完全合法、页面也能打开，但事务等于没生效——
> 只有 `stress` 的 15 项并发用例能抓出来。这也是"必须跑完 118 项才算过"的理由。

### P2：切换到 PostgreSQL（✅ 完成）

**环境**：Neon Free，区域 `aws-ap-southeast-1`（Singapore），PostgreSQL 18.6。

> 说明：首次创建的项目被放在了 Ohio（us-east-2），实测每次查询约 390 ms；
> 重建到 Singapore 后仍约 535 ms（本机有 TUN/VPN，跨境 RTT 占主导）。
> 但 Render 服务与 Neon 同在 Singapore，线上应为毫秒级——详见 §3.6。

**数据库形态**：7 张表 / 53 用户 / 33 课程 / 37 段排课 / 114 条选课 / 3 条公告，
库文件体积可忽略（免费额度 1 GB）。

**逐项修掉的方言与驱动差异**（每一条都是实际报错逼出来的）：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 所有课程都显示"名额已满"、候补位次 `NaN` | `COUNT(*)` 在 PG 返回 **bigint，被解析成字符串**；`"112" < 45` 恒为 false | `pg.js` 注册 int8 解析器 → Number |
| 2 | `could not determine data type of parameter $2` | 参数为 `undefined`，PG 无法推断类型 | `pg.js` 统一规整：undefined → null、boolean → 0/1 |
| 3 | 写 `meta` 表报 `column "id" does not exist` | `RETURNING id` 被无差别追加，而 meta 主键是 key | 只有 6 张有自增 id 的表才追加 |
| 4 | `--reset` 在 PG 下无效 | `dropAll` 查的是 `sqlite_master` | 按驱动分别查 `pg_tables` / `sqlite_master` |
| 5 | `INSERT OR REPLACE` 语法错误 | SQLite 专有 | 改为两库通用的 `ON CONFLICT (key) DO UPDATE` |
| 6 | 新增课程报 `parameter $2` | `WHERE code=? AND (? IS NULL OR id<>?)`，PG 无法推断只用于 IS NULL 的参数 | 按有无 id 分别拼 SQL |
| 7 | 又 4 处 `xxx is not a function` | 跨行的 `await db.run(...).lastInsertRowid` 优先级问题（上一轮只修了单行） | 写跨行修复器，补齐 9 处 |

| 检查 | 结果 |
| --- | --- |
| `npm run smoke`（PG 模式） | **77 / 77 通过**（耗时 211 秒） |

1. 这些数字反映的是**本机到云端的跨境链路**（TCP 建连仅 2 ms，说明有本地隧道接管），

2. 但**本地开发体验确实变差**：单页 1~5 秒，种子脚本 157 秒（SQLite 是 1 秒）。

### P3：并发正确性（✅ 完成，连跑 3 次全绿）

**改动**：`enrollmentService.getCourseRow(courseId, forUpdate)` 增加行锁开关。

```js
// PostgreSQL 用 FOR UPDATE 锁课程行；SQLite 不支持该语法，靠 BEGIN IMMEDIATE
const ROW_LOCK = config.db.driver === 'pg' ? ' FOR UPDATE OF c' : '';
```

加锁的**三个**写路径：`enroll` / `drop` / `cancelWaitlist`。

**为什么是 `FOR UPDATE OF c` 而不是 `FOR UPDATE`**：
查询里 `course` 与 `user` 有 JOIN，裸 `FOR UPDATE` 会连被 JOIN 的 user 行一起锁住——
同一个老师的两门课会被迫串行。加 `OF c` 只锁课程行，不同课程仍可并行。

口令**保持原值**（轮换已回滚），`.env` 与 Render 两处一致，服务正常。

## 九、口令轮换：第二次尝试（仍回滚，但找到根因）

### 9.1 这次先做了一件正确的事

上一次的教训是"改了库密码却更新不了 Render"。
这次**先验证了 Render 的保存能力**：给连接串加一个无害参数 `application_name=rotatecheck`，
保存后触发的部署成功 → 说明保存链路可用。

### 9.2 找到了上次失败的真正原因

**Render 的环境变量输入框是"追加"，不是"替换"。**

第一次尝试时，我在输入框里直接输入新串，结果字段变成了：

```
.../neondb?sslmode=requirepostgresql://neondb_owner:npg_xxx@.../neondb?sslmode=require
```

两段 URL 拼在一起 → 连接串非法 → seed 失败 → 部署失败。
表现和"环境变量没保存"一模一样，所以上次误判成了"保存不生效"。

正确姿势：**先 `Ctrl+A` 全选，再输入**（两步分开执行），并在保存前检查字段值是不是单条 URL。

### 9.3 为什么这次仍然回滚了

保存链路验证通过后，我用 `ALTER ROLE` 把库口令改成新值（本地验证连通 53 用户），
准备同步更新 Render 时，**"Edit" 按钮在自动化下点不动了**——
多次点击后字段仍是 `readonly=true`，编辑模式没进入。

此时线上已经连不上库（库是新口令、Render 还是旧口令），
所以优先**立即止损**：把库口令改回原值，`.env` 同步改回，线上恢复（`dbOk=true`，冒烟 77/77）。

### 9.4 结论

| 环节 | 状态 |
| --- | --- |
| Neon 改口令（SQL `ALTER ROLE`） | ✅ 可靠，秒级生效 |
| Render 保存环境变量 | ⚠️ 可行但入口（Edit 按钮）在自动化下点击不稳定 |
| 判断新口令是否生效 | 必须**重启后**看 `dbOk`，旧连接会伪装成正常 |

**远程代操作到此为止**。剩下的一步（在 Render 填新值）由人工点击 30 秒即可完成，
比继续用自动化试探更安全——每次失败都是真实的生产中断。

### 11.5 验证中遇到的两个"假故障"

1. **线上选课返回 302 但没生成记录** —— 不是故障，是业务规则正确拒绝：
   该学生已选的「日语入门」与目标课时间冲突（`CONFLICT`）。
   换一个 0 选课的学生后正常。
2. **`curl: (35) schannel: failed to receive handshake`** —— 本机到 Render 的 TLS 握手偶发失败，
   重试即可，与系统无关。

> 这两条值得记：**验证脚本"失败"不等于系统故障**，先看业务返回码与错误信息再下结论。
