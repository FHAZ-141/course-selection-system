# 05 · 新增功能标准流程

> 回答：想加一个功能，要走哪几步？每一步产出什么？怎么保证不破坏已有功能？

---

## 一、总览：七步法

```
① 确认需求  →  ② 建任务  →  ③ 设计并写模块文档  →  ④ 改数据结构
                                                        ↓
                  ⑦ 提交推送  ←  ⑥ 测试  ←  ⑤ 写代码（服务 → 路由 → 页面）
```

**核心要求：每一步都有产出物，且文档与代码在同一个提交里。**

| 步骤 | 产出物 | 落到哪个文件 |
| --- | --- | --- |
| ① 确认需求 | 需求条目（编号 F/D/B/C…） | `docs/00-需求确认清单.md` |
| ② 建任务 | 任务清单条目 | 任务管理工具 |
| ③ 设计 | **模块文档**（职责、接口、数据流、扩展点） | `docs/dev/modules/<模块名>.md` |
| ④ 改数据结构 | 两套建表语句、演示数据 | `src/db/schema.sql` + `src/db/schema.pg.sql`、`src/db/seed.js` |
| ⑤ 写代码 | 服务层 → 路由层 → 页面 | `src/services/`、`src/routes/`、`views/` |
| ⑥ 测试 | 冒烟用例 + 手工验证记录 | `test/smoke.sh` |
| ⑦ 提交推送 | 提交记录 | GitHub |

---

## 二、逐步骤详解

### ① 确认需求

先问：**这个功能属于已确认的需求范围吗？**

- 属于 → 直接开始，引用需求编号（如 §2.1-1、B4）。
- 不属于 → **先改需求基线**，在 `docs/00-需求确认清单.md` 中新增条目并注明原因，
  再开工。不要偷偷加功能，否则文档和实现会脱节。

### ② 建任务

为每个可独立验证的功能建一条任务，描述里写清验收标准。
**不要**一个任务包住三个模块——粒度太粗就无法逐项标记完成。

### ③ 设计并写模块文档（**最容易跳过、但最重要的一步**）

在写代码**之前**，先按模板写出模块文档。这一步的价值在于：
逼自己把接口和数据流想清楚，避免写到一半发现设计有问题而返工。

模板见本文第三节。

### ④ 改数据结构

1. **两套 schema 都要改**：`src/db/schema.sql`（SQLite）与 `src/db/schema.pg.sql`（PostgreSQL）。
   两边的字段名、约束、索引必须保持一致，只有类型可能不同
   （如 `AUTOINCREMENT` vs `GENERATED ALWAYS AS IDENTITY`、`REAL` vs `DOUBLE PRECISION`）。
2. 若新增字段有演示意义，同步更新 `src/db/seed.js`（它同时服务两种库）
3. 更新 `docs/dev/02-数据库设计说明.md`：字段表 + 变更记录
4. 本地验证：
   ```bash
   DB_DRIVER=sqlite npm run reset-db     # 离线先验证
   npm run reset-db:pg                   # 云端（约 2.5 分钟）
   ```
5. 若已有业务代码引用了旧字段，用全局搜索确认所有使用点都改到了
6. **注意 PostgreSQL 的两个坑**：`user` 是保留字（建表与查询都要引号，驱动已自动处理）；
   只用于 `IS NULL` 比较的参数无法推断类型（改写成按条件拼 SQL）

### ⑤ 写代码：自下而上，三步走

**顺序很重要**：服务层 → 路由层 → 页面。反过来的话，页面写完了没有数据来源，只能瞎猜接口。

1. **服务层** `src/services/<模块>Service.js`
   - 业务规则都在这里；需要多次数据库操作时用 `db.transaction()`
   - 入参只收原始值（id、字符串），不接收 `req`
   - 统一返回结构：`{ ok: true, data }` 或 `{ ok: false, code, message }`，
     便于路由层和测试脚本共用
2. **路由层** `src/routes/<模块>.js`
   - 挂鉴权：`router.use(requireLogin, requireRole(...))`
   - 只做：取参数 → 调服务 → 按结果 `render` / `redirect`
3. **页面** `views/...`
   - 必须 `include('partials/header')` 与 `include('partials/footer')`
   - 错误提示用统一的 `alert alert-error` 样式

### ⑥ 测试

1. 把新功能的**关键路径与边界**加进 `test/smoke.sh`
2. 至少覆盖：正常路径、权限越权、参数非法、业务拒绝（如满员、冲突）
3. 跑一遍全量冒烟测试，**确认没有打破已有功能**
4. 在模块文档的"验证记录"里写明测了什么、结果如何

### ⑦ 提交推送

一个功能一个提交，提交信息引用需求编号：

```
feat: 实现课程查询（§2.1-1）

- 新增 courseService：支持按课程名/教师/院系/星期筛选
- 新增 /courses 与 /courses/:id 路由与页面
- docs/dev/modules/课程查询.md 记录设计
- test/smoke.sh 补充 4 个用例
```

推送前确认远程连接正常；本项目所在网络对 git 协议偶发拦截，失败时**重试即可**，不要改方案。

## 三、模块文档模板

新建 `docs/dev/modules/<模块名>.md`，按下方结构填写（可删减，但不要跳过"数据流"与"扩展点"）：

```markdown
# 模块：<模块名>

> 对应需求：<编号，如 §2.1-1 课程查询>
> 相关文件：<列出本模块涉及的源文件>

## 一、职责

一句话说明这个模块负责什么、不负责什么。

## 二、对外接口

| 方法 | 路径 | 权限 | 入参 | 返回 |
| --- | --- | --- | --- | --- |

## 三、数据流

从请求进入到返回结果，逐层说明经过了哪些处理、读写哪些表。

## 四、业务规则

逐条列出本模块实现的规则，标注来源：
- 规则内容 —— 来源：R4 / 需求 C3

## 五、边界与异常

| 情况 | 处理方式 |
| --- | --- |

## 六、扩展点

将来若要支持 XXX，应改哪里。

## 七、验证记录

| 日期 | 验证内容 | 结果 |
| --- | --- | --- |
```

## 四、修改已有功能的流程

修改比新增更容易出错，务必多一步"影响面确认"：

1. **定位**：用 `docs/dev/README.md` 第五节的"我想改 XXX"速查表找到入口文件
2. **查影响面**：全局搜索该函数 / 字段 / 路由的所有引用点，列出会被影响的功能
3. **改服务层**：业务规则改动优先在服务层完成，路由层尽量不动
4. **回归测试**：跑全量 `npm run smoke`，重点验证受影响的功能
5. **同步文档**：模块文档的"业务规则"、"边界与异常"、"验证记录"三节必更
6. **提交**：`fix:` 或 `refactor:` 前缀，说明改了什么、为什么

## 五、接续开发前的检查清单

每次重新开始开发（例如隔了几天）前，建议先确认：

- [ ] `git pull` 拉取最新代码
- [ ] `npm install`（若 `package.json` 有变化）
- [ ] `npm run init-db`（幂等，不会覆盖已有数据）
- [ ] `npm start` 能正常启动
- [ ] 用 `admin` / `T1001` / `2024010101` 三个账号各登录一次
- [ ] 阅读 `docs/dev/modules/` 下最近新增的模块文档，恢复上下文
