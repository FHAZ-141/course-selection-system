# 开发者文档

> **目的**：让任何人（包括几个月后的你自己）在**修改或新增功能**时，不必重读全部代码，就能知道"该改哪个文件、怎么改、改完要注意什么"。

---

## 一、先明确两类文档

本项目有两套文档，**不要混淆**：

| 类型 | 位置 | 读者 | 作用 |
| --- | --- | --- | --- |
| **课程交付文档** | `docs/`（`00-需求确认清单.md`、`01-需求规格说明书.md` …） | 老师 / 评审 | 软件工程作业要求的正式文档与 UML 图表 |
| **开发者文档** | `docs/dev/`（本目录） | 开发者（你和我） | 维护、扩展、排错时用的工程手册 |

本目录属于后者。课程交付文档的规划见 [`docs/README.md`](../README.md)。

## 三、文档与代码的同步规则

**核心原则：代码和文档在同一个提交里一起更新，不允许"先写代码、文档以后补"。**

| 情况 | 必须同步更新的文档 |
| --- | --- |
| 新增一个业务模块 | `docs/dev/modules/模块名.md`（新建）+ 本目录索引 |
| 新增 / 修改路由或页面 | `03-接口与页面规范.md` |
| 新增表、字段、索引 | `02-数据库设计说明.md` |
| 改变分层或目录结构 | `01-架构与代码地图.md` |
| 新增环境变量、命令、依赖 | `04-运行与维护手册.md` |
| 任何用户可见的行为变化 | `CHANGELOG.md` |
| 需求范围发生变化 | `docs/00-需求确认清单.md`（需求基线，改动需注明原因） |

## 四、提交规范

采用约定式提交，一个提交只做一件事：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feat:` | 新功能 | `feat: 实现课程查询（F1）` |
| `fix:` | 缺陷修复 | `fix: 修正相邻时段被误判为冲突` |
| `docs:` | 仅文档 | `docs: 补充数据库设计说明` |
| `refactor:` | 重构（行为不变） | `refactor: 抽出冲突判定到独立服务` |
| `test:` | 测试相关 | `test: 补充选课并发用例` |
| `chore:` | 构建、依赖、杂项 | `chore: 升级 express` |

**每个业务模块完成后即提交并推送**，保持版本可追溯。

## 五、快速定位：我想改 XXX，该看哪里？

| 我想做的事 | 先看 | 再改 |
| --- | --- | --- |
| 加一个新页面 / 新接口 | `03-接口与页面规范` | `src/routes/` + `views/` |
| 给课程加一个字段（如"课程简介"已有、想加"课程类别"） | `02-数据库设计说明` | `schema.sql` + `seed.js` + 对应 service / view |
| 改选课的校验规则 | `modules/选课与退课.md` | `src/services/enrollmentService.js` |
| 改时间冲突的判定方式 | `modules/时间冲突检查.md` | `src/services/conflictService.js` |
| 改权限（谁能访问什么） | `03-接口与页面规范` 的权限矩阵 | `src/middleware/auth.js` + `src/routes/*.js` |
| 加一个新的角色 | `01-架构与代码地图` | `config.js` 的 `roles`、`schema.sql` 的 CHECK 约束、各路由的 `requireRole` |
| 程序起不来 / 报数据库错误 | `04-运行与维护手册` 的故障排查 | — |

## 六、写文档的三条要求

1. **写"为什么"，不只写"是什么"**。代码已经说明了"是什么"，文档的价值在于记录**取舍理由**——例如"为什么候补顺序用独立的 `waitlist_joined_at` 而不是 `created_at`"。
2. **记录踩过的坑**。凡是让人 debug 超过 10 分钟的问题，都要写进对应文档，并注明现象、根因、对策。
3. **保持可执行**。文档里的命令、路径、字段名必须和代码一致；改代码时顺手改文档，别留过期内容。
