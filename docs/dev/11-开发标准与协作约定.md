# 11 · 开发标准与协作约定

> **用途**：把本项目"怎么做才对"固化成可执行的规则，避免下一个人（或下一个 AI 会话）
> 重新踩坑。所有规则都对应到具体文件或命令，不是口号。
>
> 适用范围：v4.0.0 起的所有改动。历史文档（D1~D6）里的过程记录不受本文约束。

---

## 一、版本与发布

| 规则 | 说明 |
| --- | --- |
| 版本号 | `MAJOR.MINOR.PATCH`（semver）。当前基线 **4.0.0**；`v0.x` 为课程作业期，不再沿用 |
| 唯一版本源 | `package.json` 的 `version`。页面页脚、`/health`、`start.js` 横幅都从这里读，不要写死 |
| 发布动作 | 改版本 → 更新 CHANGELOG → 提交 → 打 tag → 推送 tag → 建 GitHub Release |
| tag 规范 | 三段式 `v4.0.0`（与历史 `v0.3.0` 一致）；Release 名称可用简称（如 `v4.0`） |
| 部署 | `render.yaml` 中 `autoDeploy: true`：推送 `main` 即自动上线；发布前务必确认测试通过 |
| 发布包 | `release/*.zip` 不入库（`.gitignore`），通过 GitHub Release 附件分发 |

### 发布检查清单

```text
[ ] npm run test:conflict          # 26 项
[ ] npm run stress                 # 15 项
[ ] npm run smoke                  # 77 项（需服务在跑；建议对离线实例跑，避免污染云端演示数据）
[ ] 本地 /health 返回 db=pg、dbOk=true
[ ] 线上 /health 的 commit 与本地 HEAD 一致
[ ] 本地写 → 线上读、线上写 → 本地读 各验证一次
[ ] npm run pack:submission        # 若 docs/ 下的交付文档有改动
[ ] 版本号在 package.json / CHANGELOG / README / PROGRESS / 文档头 一致
```

## 二、提交规范

- 采用 **Conventional Commits**：`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`。
- **一次提交只做一件事**；代码与对应文档必须同一提交（历史约定，不要"先代码后文档"）。
- 提交信息用中文描述"改了什么、为什么"，不写"update"这类空话。
- 推送失败时不要改方案：本机到 GitHub 偶发 `CONNECT tunnel failed, response 502`，
  间隔 15~20 秒重试即可（见 HANDOFF 第五节）。
- 提交前确认：`git status` 里没有 `.env`、`data/`、`node_modules/`、`release/`。

## 三、代码分层

```text
src/routes/      取参 → 调服务 → 渲染/flash，不写 SQL
src/services/    业务规则（事务、校验、状态流转），返回 { ok, code, message, data }
src/db/          驱动分发（index.js）、SQLite（sqlite.js）、PostgreSQL（pg.js）、schema、seed
src/middleware/  登录、角色鉴权、flash 注入
src/utils/       纯函数与小工具（format / password / url / flash / loadEnv / dbStatus）
views/           EJS 模板（服务端渲染，不引前端框架）
public/          CSS 与少量原生 JS（如 db-status.js）
```

硬性规则：

1. **业务规则只写在服务层**：路由与压测脚本复用同一套判定（见 `docs/03` 第 2 章）。
2. **服务层不抛业务异常**：业务拒绝返回 `{ ok:false, code:'ALREADY_ENROLLED', message }`；
   只有真正的程序错误才 `throw`，交给统一错误处理。
3. **数据库全部异步**：`db.run/get/all/transaction` 都要 `await`（PG 驱动是 Promise）。
4. **新增路由必须挂鉴权**：模块级 `router.use(requireLogin, requireRole(...))`，
   或单路由显式传入；漏挂 = 越权漏洞（冒烟测试有专门用例）。
5. **写操作成功后 POST + 重定向（PRG）**；校验失败重新渲染表单并保留输入。
6. 新增工具函数放 `src/utils/` 并补注释；不要为一个小功能引入新依赖。

## 四、数据库规范

- **两套 schema 必须同步改**：`src/db/schema.sql`（SQLite）与 `src/db/schema.pg.sql`（PostgreSQL）。
- 改表结构后同步 `docs/04-数据库设计文档.md` 的数据字典与变更记录。
- **禁止对云端库执行 `reset-db:pg`**，除非明确要清空演示数据；`start:prod` 保持幂等，绝不加 `--reset`。
- 本地与线上共库：连接串只放根目录 `.env`（不入库）；模板见 `.env.example`。
- 启动时会自动加载 `.env`（`src/utils/loadEnv.js`），进程环境变量优先；
  显式 `DB_DRIVER=sqlite` 可强制离线。
- 新增查询走参数化；PG 的 `?` 占位符由 `src/db/pg.js` 统一转换，不要手写 `$1`。

## 五、测试标准

| 脚本 | 断言 | 何时必须跑 |
| --- | --- | --- |
| `npm run test:conflict` | 26 | 改冲突判定 / 周次逻辑时 |
| `npm run stress` | 15 | 改选课、退课、候补、容量、事务时 |
| `npm run smoke` | 77 | 改路由、权限、页面、flash 文案时；发布前必跑 |

- 三个脚本合计 **118 项**，全部通过才算"功能无问题"。
- `smoke` 会写数据（选课/退课），对云端库跑会留下 `dropped` 行；
  日常回归建议起一个离线实例（`DB_DRIVER=sqlite DB_FILE=<临时文件>`）再跑。
- 新增功能必须补测试；修 bug 必须能说明"哪个断言原本会失败"。
- 测试失败时不要只改断言期望值；先确认是代码错还是文档错（历史 BUG-04 的教训）。

## 六、文档标准

- `docs/` 是交付文档（D0~D6），`docs/dev/` 是维护文档（DV1~DV11），两者都不放临时笔记。
- 每个业务模块一份 `docs/dev/modules/<模块>.md`（职责、接口、数据流、规则、边界、扩展点）。
- 改动 `docs/` 下 D0~D6 后必须执行 `npm run pack:submission` 重新生成 `提交材料/`。
- 文档里的数字（提交数、行数、测试数、链接数）**只在发布时更新**，并写明统计时点；
  平时引用 `PROGRESS.md` 的快照，不要把数字复制到多处。
- 相对链接要能在仓库内点开；发布前跑一次链接检查（见 `docs/dev/` 现有脚本或手工 grep）。
- 文档头必须写"对应代码版本"，与 `package.json` 保持一致。

## 七、安全与密钥

| 项 | 约定 |
| --- | --- |
| 连接串 / 密钥 | 只放 `.env`（已 gitignore）或部署平台环境变量；**绝不提交** |
| 口令 | `scrypt` + 每用户独立随机盐；数据库不存明文 |
| 越权 | 路由级角色校验 + 查询条件内嵌 `teacher_id`（不依赖事后判断） |
| 开放重定向 | `safeInternalPath` 只允许站内路径 |
| XSS | EJS 默认转义；公告正文不解析 HTML |
| CSRF | **未实现**（已知缺口，见 D1 §5.2）；如要补，先加 token 校验中间件并补测试 |
| 演示口令 | `123456`，仅限教学演示；正式使用必须改密并加强度校验 |

## 八、审查与一致性

每次较大改动后，按这张清单核对（v4.0.0 前的审计就是按它发现问题的）：

| 类别 | 检查内容 |
| --- | --- |
| 版本 | `package.json` / CHANGELOG / README / PROGRESS / 文档头 是否一致 |
| 路由 | `docs/dev/03` 的 URL/方法/权限 与 `src/routes/*.js` 是否一致 |
| 接口 | `/health` 返回字段与文档描述是否一致 |
| 数字 | 提交数、代码/文档行数、测试数、链接数（发布时更新） |
| 状态 | "已完成/待办/未发布"的表述是否互相矛盾（典型：F3 已上线却仍写 TODO） |
| 类设计 | 服务类/工具类数量与 `src/services`、`src/utils` 实际文件数一致 |
| 数据 | 演示数据规模、验收标准里的具体数字能否由 seed 复现 |
| 链接 | `docs/` 内相对链接 0 断链 |
