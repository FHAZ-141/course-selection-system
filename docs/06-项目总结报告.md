## 四、技术难点与解决方案

### 4.1 数据库驱动的参数绑定陷阱（最难查的一个）

**现象**：写入数据库的数字参数全部变成 `NULL`，但**不报任何错**。

**分析**：项目用的 `node-sqlite3-wasm` 与常见驱动（`sqlite3`、`better-sqlite3`）不同，
它对可变参数形式的调用只绑定第一个参数：

```js
db.run('INSERT INTO t (a, b) VALUES (?, ?)', 1, 2)   // ❌ 只有 1 被绑定，2 丢失
db.run('INSERT INTO t (a, b) VALUES (?, ?)', [1, 2]) // ✅ 正确
```

**为什么难查**：不抛异常、不写日志，数据就是"悄悄少了一半"。
直到页面上显示"容量为 null"才被发现。

**方案**：数据访问层统一加 `normalizeParams()`，把可变参数规整成数组再传下去。
应用代码仍然可以自然书写，风险收敛在一处。

**教训**：**换驱动时不能假设 API 语义一致**。这个坑如果没在数据层收口，
会散落在几十处调用里，改都改不完。

### 4.2 并发选课不超卖

**问题**：10 名学生几乎同时点"选课"，容量只有 3，如何保证不多发名额？

**分析**：选课的不变式是「已选人数 ≤ 容量」，它跨越"读余量"和"写记录"两步。
如果两次操作之间没有隔离，两个请求可能同时读到"还有 1 个名额"，然后都写入。

**方案**（三层保障）：

| 层 | 手段 | 作用 |
| --- | --- | --- |
| 事务 | `BEGIN IMMEDIATE` 开启即取写锁 | 校验与写入不被打断，避免锁升级死锁 |
| 计数 | 事务内实时 `COUNT(*)` | 不信任页面上显示的旧余量 |
| 约束 | `UNIQUE(student_id, course_id)` | 重复提交只成功一次 |

**效果**：实测 10 抢 3 → 选中 3、候补 3、拒绝 4，**闭合且零超卖**。

**代价**：热点课程上的请求被串行化。这是 L1 记录的限制，演示规模可接受。

### 4.3 候补补位的"跳过顺延"

**问题**：退课释放一个名额后，候补队首如果此时与自己的已选课程冲突，怎么办？

**三个方案对比**：

| 方案 | 结果 |
| --- | --- |
| 直接补给他 | ❌ 制造了新的时间冲突，规则形同虚设 |
| 把他移出队列，补下一位 | ❌ 对"临时冲突"的学生过严，且他可能下轮就能补上 |
| **跳过、顺延下一位，保留他的队列位置**（采用） | ✅ 名额不浪费，学生不吃亏 |

**实现要点**：`promoteNext` 里遍历队列，遇冲突 `continue` 而不是 `delete`；
且**一次退课只补一个人**（否则会超容量）。

**这个逻辑用文字描述极易被理解错**，所以 D3 里单独画了一张活动图，
把"跳过"和"补位"两条分支并列展示。

### 4.4 SQLite 锁与异常自愈

> 本节记录的是 SQLite 模式下的问题；2026-10-22 迁移 PostgreSQL 后该路径已不再是主链路，
> 但代码保留以支持离线开发。

**现象**：启动报 `database is locked`，重启仍然复现。

**分析**：两层原因叠加——
1. `prepare()` 之后没有 `finalize()`，写语句一直持锁；
2. 异常退出（比如在写事务中按 Ctrl+C）会残留锁目录，下次启动仍然撞上。

**方案**：
- 改用 Database 级 `run/get/all`（内部自动 finalize），不再手工管理语句句柄；
- 启动时检测并清理残留锁目录，同时打印一行提示说明原因。

**效果**：连续多次启动、异常退出后重启均正常。这条自愈逻辑后来在多次调试中反复救场。

### 4.5 时间冲突的三条件判定

**判定式**：星期相同 **且** 节次真正重叠 **且** 周次有交集。

三处容易做错：

| 点 | 易错做法 | 正确做法 |
| --- | --- | --- |
| 节次 | 用"区间不相交"取反 | 用闭区间判重叠：`a.start ≤ b.end && b.start ≤ a.end`，**相邻不算冲突** |
| 周次 | 只比较起止周 | 先求区间交集，再逐周判断单双周是否相容 |
| 参数 | 把"同一门课"也拿去比 | 排除目标课程自身 |

**收益**：把这个判定抽成纯函数后，26 条边界用例可以秒级跑完。
如果留在路由里，每条用例都要造一组课程数据，根本测不动。

### 4.6 从 SQLite 迁移到 PostgreSQL（2026-10-22）

**触发原因**：需求演进出"本地改的数据，线上立刻能看到"。SQLite 的单文件特性成了硬障碍——
两台机器无法共享同一个库文件，放到网盘/网络盘上会因文件锁失效而损坏（SQLite 官方警告）。

**方案**：Neon 托管的 PostgreSQL 18（Singapore），本地与 Render 同连一个库；
保留 SQLite 作为离线开发与回退（`DATABASE_URL` 是否存在自动切换）。

**四个阶段**（每阶段独立验收，见 `dev/08-迁移执行记录.md`）：

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 数据层拆双驱动 + PG schema | 118/118（SQLite，证明未破坏） |
| P1 | 服务层与路由全量异步化（45 个函数） | 118/118（SQLite） |
| P2 | 切 Neon、修 7 类方言差异 | 77/77（PostgreSQL） |
| P3 | `SELECT ... FOR UPDATE` 行锁 | 并发连跑 3 轮 15/15 |

**三个最值得记的坑**：

1. **`COUNT(*)` 在 PG 返回 bigint，被解析成字符串**——`"112" < 45` 恒为 false，
   表现为"所有课程都显示已满、候补位次 NaN"。页面不报错，只有断言能抓到。
2. **事务提交早于回调完成**：`transaction(fn)` 若不 `await fn()`，`COMMIT` 会在异步回调
   跑完前执行，事务等于没生效。语法合法、页面正常，只有并发用例能抓。
3. **`await` 的优先级陷阱**：`await db.get(...).c` 等价于 `await (get().c)` → undefined。
   全仓共 21 处，且**跨行写法占多数**，单行正则修不干净。

**结论**：迁移本身不难（逻辑结构未变），难在**类型与并发语义的差异**，
以及"看起来正常但实际错了"的静默失败。这类问题只能靠完整测试兜住。

## 五、工程实践总结

### 5.1 文档先行

每个业务模块都是**先写 `docs/dev/modules/<模块>.md`（职责、接口、数据流、边界、扩展点），再写代码**。

效果很直接：写文档时就会想清楚"异常怎么处理""这个函数该给谁用"，
真正写代码时很少返工。

### 5.2 自动化测试分层

按风险分配投入，而不是平均用力：

| 层次 | 数量 | 为什么放这一层 |
| --- | --- | --- |
| 单元 | 26 | 冲突判定边界密集，造数据成本极高 |
| 集成 | 15 | 并发与补位必须真实事务 |
| 端到端 | 77 | 权限与提示文案只在页面体现 |

**这是本项目最值得保留的实践**：测试不是"补作业"，而是设计的一部分。
4.1 节那个静默错误，就是靠断言才暴露的。

### 5.3 交付形态

从"敲三条命令"改成"双击一个文件"：

| 问题 | 处理 |
| --- | --- |
| 依赖没装 | 启动器自动 `npm install` |
| 数据库没有 | 自动初始化 |
| 端口被占用 | 自动顺延并提示实际地址 |
| 服务已在运行 | 只打开浏览器，**不重复启动**（两个进程会抢同一个 SQLite 文件） |

最后一条不是拍脑袋加的——两个实例同时写同一个库会导致锁冲突，
宁可拒绝启动也不能让它"看起来成功了"。

### 5.4 版本管理

21 次提交，4 个标签，每次提交都遵循 `feat/fix/docs/refactor/test/chore` 前缀。

**代码与文档同一次提交**是硬规矩。这条规矩救过一次：
改选课规则时同步改了模块文档，否则文档会在两周后彻底失效。

### 5.5 图表流水线

本机没有 Java（PlantUML 不可用），也装不上 mermaid-cli（网络不稳），
最后用 **Chrome 无头模式 + 本地 mermaid.js** 渲染，并把脚本固化进仓库。

10 张图统一 `.mmd` 源文件 + `.png`（2 倍分辨率）+ `.svg`（矢量）。
改图只需改源文件重跑一条命令，不用重画。

### 6.2 文档与代码对不上（发生 3 次）

**教训**：**期望值必须来自数据源，不能来自记忆。**
先查库确认，再写断言。

### 6.4 图表渲染的三个坑

| 坑 | 现象 | 根因 |
| --- | --- | --- |
| SVG 非法 XML | 浏览器打开报 "tag mismatch: br" | 默认输出 HTML 标签（`<br>` 未闭合），作为 XML 非法 |
| 状态图黑块 | 文字几乎不可见 | 用了复合状态，主题下渲染为深色填充 |
| 图太宽/太高 | 1915×331 或 867×2727，A4 放不下 | 节点串行排列，没有合并同类判定 |

**又一个坑**：Chrome 的错误页里恰好有一个 `<svg>` 图标，
我的脚本"抓第一个 svg"正好抓到它，于是**静默产出一张坏图**。

**教训**：**生成物必须独立校验，不能只看脚本有没有报错。**
现在的做法是每张图渲染后都用 Chrome 打开一次，检查是否含解析错误。

### 6.5 网络是环境的一部分

推送连续失败 20 多次，全是 `CONNECT tunnel failed, response 502`。
诊断发现：`api.github.com` 和 `codeload.github.com` 都通，**只有 `github.com` 不通**，
curl 显示代理隧道建立后卡在 TLS 重协商。

试过 `http.version=HTTP/1.1`、`sslBackend=openssl`、加大重试间隔，**都无效**，
最后等了十几分钟自己恢复。

**教训**：**外部依赖的失败要能定位到具体环节**（DNS / CONNECT / TLS / 应用层），
否则只能盲目重试。判断出"只有 github.com 挂"之后，就知道不是自己的配置问题，
耐心等即可，不必改代码或改配置。

## 八、收获与体会

**关于"能跑"和"交付"的距离**

代码写完只是开始。真正花时间的部分在：别人能不能装上、能不能启动、
出错时看不看得懂提示、改了功能文档会不会失效。
一键启动器、错误提示文案、变更记录，这些"不产生新功能"的工作占了相当大的比重，
但它们决定了交付物能不能被使用。

**关于可测性设计**

冲突判定如果写在路由里，就只能靠页面点击验证，26 个边界根本测不动。
把它抽成纯函数后，测试成本从"每次造一组课程数据"降到"一行断言"。
**可测性不是测试阶段的问题，是设计阶段的决定。**

**关于诚实**

文档里如实写了 3 个安全缺口（无 CSRF、无限流、弱口令）、
6 项未覆盖测试、6 条技术债、9 个真实缺陷。
这些内容不会让项目显得更好看，但它们让评审方知道**边界在哪里**——
比藏着掖着、被问到时答不上来要好。

**关于自己也会犯错**

6.1 节那个编号错误，本质是"我以为我记得"。
项目里最容易出错的不是难的技术问题，而是**没有回源核对的习惯**。
后来养成的做法是：引用前先打开源文件，写完再机器校验一遍
（比如 D5 的 118 条用例编号，就是用脚本查过连续性和重复的）。
